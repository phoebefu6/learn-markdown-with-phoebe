Pictures and quotes 5 min live

Two elements, one shared idea: both borrow syntax you already know. An image is a link with a ! in front; a quote is a paragraph with a > in front.

LiveImages: a link that shows instead of takes you2.5 min▶
You type![Phoebe waving hello](https://github.com/you.png "hi!")
→
Browser shows
👋

your actual photo, rendered on the page

  • Same shape as a link, plus a bang: ![alt text](image-url "title"). The ! is the whole difference - forget it and you get a clickable link instead of a picture.
  • Alt text is not decoration - it's accessibility. Screen readers speak it, and it displays whenever the image fails to load. Describe the picture: "Phoebe hiking at sunrise", not "image1".
  • The URL must point at an actual image file (.png, .jpg, .gif...), not at a page that contains one. Your GitHub avatar has a permanent one: https://github.com/USERNAME.png.
Real world

Why pros sweat the alt text: on a slow connection, GitHub shows the alt text while the image loads - and if the link ever rots, the alt text is all anyone sees. A README full of ![](...) with empty alts degrades into mystery gaps; one with real alts still reads like a page. Accessibility and durability, one habit.

LiveBlockquotes: give words a stage2.5 min▶
You type> Ship early, ship often. > > Two lines, one quote - > every line carries the >.
→
Browser shows

Ship early, ship often.

Two lines, one quote - every line carries the >.

  • One character: start the line with > and it renders as an indented, styled quote block. Anything can live inside - bold, links, even lists.
  • The gotcha that gets everyone: a blank line INSIDE a quote must also carry the >, alone on its line. A truly empty line ends the quote, and the second half falls out as a normal paragraph. This is quiz question one - and Demo 3 breaks it live.
  • Nesting: >> quotes a quote - the reply-to-a-reply look you know from email.
Self-studyLinked images + an escaping recap2 min read▶
  • A clickable image is an image wrapped in a link: [![alt](image-url)](target-url). Read it inside-out: the image renders, the outer brackets make it a link. Badges in Session 3 use exactly this.
  • Escaping recap from Session 1: to show a literal !, > or bracket, backslash it: \> not a quote. The full escapable set is on your Session 1 cheat sheet.
  • Image sizing: pure markdown has none. Where you need it (and GitHub allows it), drop to HTML: <img src="..." width="300">. More HTML workarounds in Part 3.

Code that looks like code 4 min live

Even a non-programmer's page mentions technical things - keyboard shortcuts, file names, commands. Markdown gives them a monospace costume so they read as "type this exactly", two ways: inline and block.

LiveInline code: backticks around the words1.5 min▶
You typePress `Ctrl+S` to save, then run `git status` to check.
→
Browser shows

Press Ctrl+S to save, then run git status to check.

  • The backtick ` is the key next to 1 (not an apostrophe!). Wrap file names, shortcuts, commands, anything meant literally: `README.md`.
  • Bonus power: inside backticks, markdown is OFF. `**not bold**` shows the stars - handy for writing ABOUT markdown.
LiveFenced code blocks: three backticks build a wall2.5 min▶
You type```python print("hello, markdown") ```
→
Browser shows
print("hello, markdown")

a shaded block, colored by language

  • Open with ``` on its own line, close with ``` on its own line. Everything between renders exactly as typed - spacing, stars, hashes, all literal.
  • Name the language after the opening fence - ```python, ```sql, ```html - and renderers that support highlighting color it. The info string is standard CommonMark; whether colors actually appear is up to the renderer. GitHub: yes.
  • An unclosed fence swallows the rest of your page. If everything below a code block suddenly turns monospace, you forgot the closing ```. Demo 3 does this on purpose.
Real world

The most-typed markdown at work: pasting an error into a chat or GitHub issue inside a ``` fence. Unfenced, the error's underscores and brackets get mangled into italics and links; fenced, it arrives character-perfect and the person helping you can actually read it. People notice who fences.

Self-studyThe old way, and backticks inside backticks2 min read▶
  • Indented code blocks: before fences existed, indenting a line 4 spaces made it code - which is exactly why Session 1 warned you never to indent paragraphs. You'll meet this in older documents; write fences yourself, they're clearer and they take a language name.
  • A literal backtick inside inline code: wrap with DOUBLE backticks: `` a ` inside ``. Rare, but unforgettable once you've needed it.
  • Code inside a list item: a fence works, or indent the code 8 spaces (4 for the list nesting + 4 for code).

Tables and checklists - your first GFM 5 min live

Milestone moment: everything until now was core markdown that works everywhere. Tables and task lists are extended syntax - GitHub Flavored Markdown (GFM). Not every app renders them, but GitHub does, and GitHub is exactly where your page lives. Welcome to the dialect of your new home.

LiveTables: pipes for columns, dashes for the header line2.5 min▶
You type| Skill | Level | | --- | --- | | Excel | strong | | Python | learning |
→
Browser shows
SkillLevel
Excelstrong
Pythonlearning
  • Three rules: pipes | separate columns, row one is the header, and row two MUST be dashes (---, at least three per column). No dash row, no table - just a paragraph full of pipes. The #1 table bug.
  • Columns don't need to line up in the source. Ragged pipes render as a perfect grid - the renderer does the alignment, not you. (Lining them up anyway is a kindness to whoever reads the raw file.)
  • A literal pipe in a cell needs escaping: \|.
LiveColumn alignment: colons steer the dashes1 min▶

Add colons to the dash row to control each column: :--- left, :---: center, ---: right. Memory hook: the colon is a magnet - the text sticks to its side.

:--- left:---: center---: right
wordslevels1,240

Right-align number columns and they read like a spreadsheet; center short status words. Small touch, instantly more professional.

  • A regular list item plus brackets: - [ ] unchecked, - [x] checked. The space inside the empty brackets matters.
  • On GitHub these are real checkboxes - in issues you can click them; on your profile they render as a live progress list. A "currently learning" checklist with one box already ticked says more about you than a paragraph could.
Say it plainly: this part is GFM Tables and task lists are extended syntax. Paste them into an app that only speaks core markdown and you'll see raw pipes and brackets - not broken, just unsupported. Rule of thumb: Sessions 1-2 core elements work everywhere; from here on, check the app. Your page's app is GitHub, which renders all of today.
Self-studyTable limits, strikethrough, and two small traps3 min read▶
  • What table cells CANNOT hold: headings, lists, blockquotes, code blocks, horizontal rules - block elements don't fit in cells. Bold, italic, links, inline code are fine.
  • The HTML workaround: need a line break inside a cell? <br>. Need a list-ish cell? item one<br>item two. Beyond that, consider whether it should be a table at all.
  • Strikethrough: ~~like this~~ renders like this - also GFM. Fun on a learning list: ~~fear of markdown~~.
  • Task-list trap: a task starting with an open parenthesis needs an escape: - [ ] \(Optional) stretch goal.

Add a new section: ## Words I live by (blank lines around it!), then your favorite quote as a blockquote: > the quote. Add an attribution line below it, also starting with >, and keep the > on the blank line between them.

Demo 2 of 3

Build your skills table and learning checklist ★ 10 min · everyone builds

New section: ## Skills. Take the 4-6 skills you collected for homework and give the table its skeleton first - header row, then the dash row: | Skill | Level | Notes | over | --- | --- | --- |. Watch the right pane: no table yet? Check the dash row.

Add one row per skill: | Excel | strong | my home turf |. Don't fuss over lining up the pipes - the renderer aligns everything for you.

Steer the columns: make Level centered with :---: in its dash cell. If you had a numbers column, ---: would right-align it.

New section: ## Currently learning. Three task-list items: - [x] Markdown basics (earned it!), then two - [ ] boxes for what's next.

Discernment lap: does the Notes column earn its place? Would a shorter table read better? Tables are for scanning - trim until they scan.

Real world

Skim the READMEs of people you admire on GitHub: the ones that stick use a small table or checklist near the top - skills, current projects, "now learning". Recruiters and collaborators scan those in seconds. Your table today is that exact asset, and Friday-you will thank Wednesday-you for the checked first box.

Demo 3 of 3

Break it on purpose, round two ★ 5 min · follow along

In your quote, delete the > from the blank line between quote and attribution. Watch the quote split - attribution falls out as a plain paragraph. Put the > back, watch it rejoin.

Delete your table's dash row. The whole table collapses into one sad paragraph of pipes. Restore the dashes - at least three per column - and the grid snaps back.

Delete the closing ``` of a code block and watch it swallow everything below it into monospace. Close the fence, page restored.

Say each diagnosis out loud: quote split = blank line lost its > · pipes showing = dash row missing · page went monospace = unclosed fence. That's the whole Session 2 debugging kit.

Why break things, again? Same logic as Session 1: a bug you've caused on purpose takes two seconds to fix when it happens by accident. These three are the bugs you WILL meet this week.

Check yourself

Three questions before you go 🎯 ◐ 90 seconds

1 · Your two-line blockquote keeps splitting in half. What's the classic cause?

A truly empty line ends a blockquote. Keep multi-part quotes together by putting a lone > on the blank line - the gotcha from Demo 3.

2 · You paste your beautiful skills table into another app and see raw pipes. Why?

Core markdown works everywhere; tables and task lists are GitHub Flavored Markdown extras. Your page lives on GitHub, so you're safe at home - but check before assuming elsewhere.

3 · What is the alt text in ![alt text](url) actually for?

Alt text is accessibility plus a safety net: it's what blind and low-vision readers hear, and what everyone sees if the image link ever breaks. Write it like a description, not a label.
